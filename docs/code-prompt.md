# Задача: сайт инженерно-изыскательской компании с калькулятором-генератором программы работ

## Контекст
Мы разобрали три сайта конкурентов:
- geocompani.ru/uslugi/prais/ — берём механику калькулятора. Это квиз: один вопрос на экран, ветвление, подсказка под каждым вариантом, результат показывается до ввода контакта.
- uralproj.ru/services/geolog/ — берём структуру контента: таблицы «этап → работы → норматив», паспорт компании, «как проверить подрядчика», FAQ.
- geo-zakaz.ru — антипример.

Дизайн ведётся по отдельному брифу (`design-brief.md`). От дизайна на вход приходят DTCG-токены и описания компонентов (`components/*.md`).

## Ключевые принципы
1. Калькулятор генерирует ПРЕДВАРИТЕЛЬНУЮ ПРОГРАММУ РАБОТ: объём с обоснованием, состав, срок, цену или вилку, допущения, что подготовить заказчику. Результат можно скачать в PDF и открыть по ссылке, которой поделились.
2. Одна истина по ценам. Тарифы и правила хранятся как данные. Из них собираются калькулятор, страница «Цены» и цифры «от …» в карточках услуг. Цифры в вёрстке запрещены.
3. Движок расчёта — чистые функции на TypeScript без UI. Каждое правило несёт текст обоснования и ссылку на норматив.
4. В каждом вопросе есть «не знаю»: подставляется консервативное допущение, и оно явно помечается в результате.
5. Коммерческий объект не упирается в тупик: клиент получает вилку цены и чек-лист исходных данных.

## ВАЖНО: достоверность
- НЕ выдумывай тарифы, нормативные значения, пункты СП/ГОСТ и реквизиты. Все цифры помечай `demo: true` и собирай в одном файле.
- Каждое нормативное правило сопровождай комментарием `// TODO: верифицировать инженером`. Список всех таких мест — в README.

## Стек — ЗАФИКСИРОВАН, не предлагай альтернатив
Источник: мой документ «Веб дизайн-система: рабочий стек» (статус: принято).

Главное правило: истина — только то, что закоммичено в git (`tokens/*.json` + React-компоненты). Макеты и прототипы — расходник.

| Слой | Инструмент |
|---|---|
| Токены | DTCG JSON, три слоя: primitive → semantic → component |
| Сборка токенов | Style Dictionary v4 → CSS-переменные (+ TS-константы) и Tailwind-пресет |
| Компоненты | React + Tailwind (пресет только из токенов) |
| Витрина / контракт | Storybook: у каждого компонента есть стори |
| Правка дизайнером | Onlook: код остаётся истиной, правки пишутся в TSX. Код и структура должны быть совместимы с Onlook |
| Гейт 1 | Stylelint/ESLint: запрет хардкода hex/px и arbitrary-значений Tailwind `[...]` |
| Гейт 2 | Playwright `toHaveScreenshot`, бейзлайны в git, генерация только в Docker в CI |

Дополнительно для этого проекта: vitest для движка калькулятора, zod для схем данных (валидация на сборке).

Структура репозитория — по документу стека:
```
tokens/{primitive,semantic,component}/
build/                      # генерируется, в .gitignore
style-dictionary.config.js
tailwind.preset.js
src/components/
.storybook/
tests/visual/
.github/workflows/ci.yml    # два гейта
```
Плюс для проекта:
```
data/          # pricing, rules, company, services
src/engine/    # движок расчёта
src/app/       # страницы
```

## Открытые решения — подтверди у меня ДО начала кода
(в скобках — вариант по умолчанию)
1. **Мета-фреймворк** (документ стека его не фиксирует):
   - (а) Next.js со статическим экспортом — родная среда для Onlook;
   - (б) Vite + React с пререндером страниц.
   (По умолчанию: а.)
2. **Отправка заявок.** Статика не принимает формы сама.
   - (а) Telegram-бот;
   - (б) email;
   - (в) webhook в CRM или 1С;
   - (г) интерфейс-адаптер с несколькими реализациями.
   (По умолчанию: г, реализованы а и б.)
3. **Хостинг.**
   - (а) российский хостинг статики / Object Storage;
   - (б) свой VPS за reverse-proxy.
   (По умолчанию: а.)
4. **Выход калькулятора.**
   - (а) точная цена для типовых частных случаев, вилка для коммерческих;
   - (б) вилка везде;
   - (в) только состав работ без цены.
   (По умолчанию: а, результат показывается до ввода контакта.)
5. **Направления MVP.**
   - (а) геология + топосъёмка;
   - (б) плюс экология и гидромет.
   (По умолчанию: а, архитектура расширяемая.)
6. **Бренд.** Пока токены-заглушки нейтральные, реальные значения придут от дизайнера.

## Калькулятор MVP
**Геология:**
- тип объекта;
- длина большей стороны или пятно застройки;
- этажность;
- подвал;
- тип фундамента (есть «не знаю»);
- кадастровый номер или точка на карте → зона выезда;
- срочность.

**Топосъёмка:**
- цель (дом/ГПЗУ, газ, вода/канализация, ландшафт);
- площадь;
- масштаб;
- площадный или линейный объект;
- подземные коммуникации;
- подеревная съёмка;
- вынос границ;
- согласование с эксплуатирующими службами.

**Пакет «геология + топо»:** скидка показывается прямо в результате.

**Результат:**
- обоснования по каждому пункту;
- допущения;
- кнопка PDF;
- кнопка «Поделиться» (состояние хранится в URL);
- кнопка «Отправить инженеру».

**UX:**
- один вопрос на экран;
- кнопка «назад» без потери ответов;
- калькулятор полностью проходится с клавиатуры;
- mobile-first.

## Страницы
Главная (входы по сценариям), Калькулятор, Цены (из модели цен), Услуги (6–10 страниц), Образцы отчётов, Объекты, О компании (паспорт), Как проверить подрядчика, Контакты, 404.

SEO: schema.org (Organization, FAQPage), sitemap.

## Порядок работы
1. Задай вопросы из блока «Открытые решения», покажи план и схемы данных. Жди подтверждения.
2. Каркас репозитория по стеку: токены-заглушки → Style Dictionary → Tailwind-пресет → один эталонный компонент со стори и снапшотом → CI с двумя гейтами.
3. Схемы данных, движок, табличные тесты. Без UI.
4. Компоненты по `components/*.md` + Storybook + снапшоты.
5. Калькулятор, PDF, шаринг.
6. Страницы из данных.
7. Заявки, SEO, Lighthouse на мобильных ≥ 90.

После каждого этапа — отчёт: что сделано, что осталось, новые TODO.

Протокол сессий: код-сессия берёт на вход git-ref, а не «то, что было в чате выше».

## Критерии готовности
- Оба CI-гейта зелёные. Цен, контактов и хардкод-стилей в вёрстке нет.
- Движок покрыт тестами по всем веткам, включая «не знаю».
- Одна правка в `data/pricing` меняет калькулятор, страницу «Цены» и карточки услуг.
- Замена токенов меняет весь визуал без правок компонентов.
- В README описано: как заполнять данные, список `demo`-значений и `TODO`, как подключить адаптер заявок.
